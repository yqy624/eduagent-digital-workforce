# EduAgent 智慧教育视觉感知平台 · 工作成果梳理

> **用途**：交给他人整理进简历 / 毕设材料
> **项目**：edu-ai-platform（EduAgent）+ 配套独立视觉服务 yolo-platform
> **整理时间**：2026-10-10
> **一句话概括**：把一个传统的「教育管理系统」，重构成以 **YOLO 视觉为源、教育业务为消费方** 的多场景 AI 智慧平台，并亲手打通「上传图片 → YOLO 推理 → 事件落库 → 身份归属 → 告警派发」的完整闭环。

## 一、项目背景

### 1.1 起点

项目前身 EduAgent 是一个**传统教育管理系统**：记录课程、作业、成绩，按角色（管理员 / 教师 / 学生）切分功能。
技术栈为 FastAPI + SQLAlchemy 2.0 Async + LangChain，后端从早期 Java 实现迁移为 Python。

### 1.2 转折点

在作为**毕业设计 + 简历展示项目**的定位下，方向被重新定义：

> **基于 YOLO 与 Agent 的多场景智慧教育视觉感知与反馈系统**

核心技术主张：**视觉是数据源，教育业务是消费方**——而不是"一个教育平台旁边并列挂一个视觉模块"。

### 1.3 覆盖的四大场景

| 场景 | 技术路径 | 是否需要训练 |
|---|---|---|
| 课堂行为识别（核心） | COCO 预训练 person + 几何规则 + 时序状态机 | 零训练 |
| 实验室安全识别 | 通用权重做阳性事件派生 | 唯一需自定义权重的场景 |
| 考场行为监测 | cell phone（COCO 内置类）+ 座位表上下文 | 零训练 |
| 拍照识别批改 | 题块定位（传统 CV）+ 人工复核队列 | 零训练 |

## 二、主要工作内容

> 按**主题**归类，每条标注「做了什么 / 为什么 / 量化证据」。

### 2.1 模型抽象层：让"换模型 = 改一个环境变量"

**做了什么**
- 设计并落地统一契约层 `app/core/models/`：
  - `contracts.py`：`ModelResult[T]` / `ModelMeta` / `ModelError`(ErrorKind) / `SceneState` / 各能力请求响应体，契约版本 `1.0.0`
  - `base.py`：模板方法模式，`invoke()` 统一做**校验 → 超时 → 熔断 → 重试 → 耗时统计**，子类只实现 `_acall()`
  - `policy.py`：超时 + 指数退避重试（默认 3 次）+ 熔断器（连续 5 次失败熔断）
  - `registry.py`：按 capability 分组注册，**配置驱动切换**，未就绪自动回落占位实现
  - `placeholders/`：确定性占位实现（同输入永远同输出，保证流程可复现、回归可测）
- 4 类能力：`vision` / `llm` / `embedding` / `retrieval`

**为什么**
- 视觉、LLM、向量化是三条完全不同的技术链路，若业务层直连具体实现，换模型就要改遍全站。

**量化证据**
- 视觉调用点在业务层**唯一**（`vision_service.py` 一处），切真实后端**业务代码零改动**
- 配置四态切换全部验证通过：不设→placeholder / `http-yolo`→http-yolo / `yolo-platform`→子进程 / 不存在→回落占位+告警
- 熔断重试零额外代码自动覆盖新传输层

### 2.2 YOLO 视觉接入与性能质变（约 65 倍提升）

**做了什么**
- 搭建独立视觉服务 `yolo-platform`（与 edu 平级独立仓库）：FastAPI + Ultralytics YOLO11n + GPU 推理
- 新增 `POST /v1/vision/infer` **常驻常驻推理服务**：进程级模型单例（双检锁）+ 推理锁（规避 ultralytics 并发 predict 竞态）+ `X-Trace-Id` 透传回显
- edu 侧新增 `HttpVisionProvider` 适配器，配置 `MODEL_VISION_BACKEND=http-yolo` 即启用

**为什么**
- 原实现**每个请求都 `create_subprocess_exec` + 重新 `load_model()`**（每次约 10 秒），
- 且 edu 侧是 CPU 版 torch（6.5 FPS）、yolo-platform 是 CUDA 版（37.6 FPS），同进程装不下两套 torch，故必须跨进程。

**量化证据**

| 路径 | 单次耗时 |
|---|---|
| HTTP 冷启动（含加载权重） | 11.57 s |
| **HTTP 稳态** | **0.056 s** |
| 子进程（历史） | 10.71 s / 11.66 s |

- **约 65 倍提升**；GPU 推理 RTX 4060 Laptop 上 **26.63 ms / 37.6 FPS**，显存峰值仅 0.11 GB
- traceId 端到端逐字符一致，熔断/重试/四态切换全部实测通过

### 2.3 平台功能模块重构：从「按角色切」到「按能力切」

**做了什么**
- 诊断出原系统的根因：主干按**角色**（admin/teacher/student）切分，导致加新能力要改三个文件，菜单天然长成"教育平台"的样子
- 重构为**六大能力模块**，角色降级为权限属性：

| # | 一级模块 | 定位 |
|---|---|---|
| 1 | 视觉感知中枢 `vision` | 平台核心引擎与数据源 |
| 2 | 智能评阅 `review` | 作业全生命周期，人工 + AI 双通道 |
| 3 | 学情洞察 `insight` | 消费视觉与评阅数据，产出画像与预警 |
| 4 | 知识智能 `knowledge` | RAG 检索与 Agent 对话 |
| 5 | 态势感知与告警 `situation` | 统一看板 + 实时告警总线 |
| 6 | 平台治理 `governance` | 身份权限、审计、模型与算力资产、存储 |

- 后端新增 4 个薄封装命名空间 router（`governance` / `situation` / `knowledge` / `insight`），
  策略是**薄封装复用现有 service，不重写业务**，AI 相关一律延迟 import 避免拖垮启动

**量化证据**
- 后端真实路由 **119 → 151 → 156 条**
- 菜单 **6 大模块 / 49 项能力**，复用现成 24 · 改造 4 · 新建 21（**复用率 49%**）
- 21 项新建中 11 项属视觉模块（视觉确实先行）

**关键设计判断**
- **课程刻意不升为一级菜单**——课程一旦独立，教育属性就会盖过视觉属性
- **`/api/vision/*` 物理隔离**——为将来抽成独立服务预留

### 2.5 视觉感知链路打通 + 事件派生层

**做了什么**
- 诊断出**三处叠加断链**并全部修复：
  1. edu 上传的图片从未在真模型下跑通（历史任务全是占位或 yolo 内部路径）
  2. `classroom` / `lab_safety` 完全没有上传入口
  3. 真模型路径的事件**恒为空**（原 `events=[]` 硬编码）
- 上传接口新增 `vision_scene` 参数 → **上传即感知**
- **新建事件派生层 `_event_derivation.py`**：把"检测事实"翻译成"语义事件"

**派生层的三条自我约束（答辩核心）**
1. **只做阳性派生，不做阴性判断** —— 通用权重没有 goggles/gloves 类别，拿它的沉默报"未佩戴"= 把模型短板说成学生违规
2. **不做时序推断** —— 单帧推不出"持续低头"，故 `duration_s` 恒 0
3. **事件必须可追溯** —— evidence 带 `cls_name / conf / bbox`，人能回原图核对

**两种执行节奏**
- 需人工复核（拍照批改）：只登记 `pending`，教师触发（批改影响分数，不能让模型跑完就落分）
- 自动感知（课堂/实验室/考场）：登记后立刻后台执行

**量化证据**
- 首次打通：classroom 488ms 产出 `class_present 在场人数 4`；lab_safety 139ms 产出 `operators_present`
- 8 项边界全部正确（人工复核边界、非图片不误触发、向后兼容、去重、场景隔离、消费端可读）
- 有说服力的对比：旧占位实现产出**编造的** `no_goggles 未佩戴护目镜`；新真模型路径产出真实的 `operators_present` + 明确声明"护目镜判断需专用权重"——**"宁可少报，不伪造告警"**

### 2.6 微服务化：RAG 检索外置（对接 rag-go）

**做了什么**
- 对接独立 RAG 服务 `rag-go`（Go 技术栈：MinIO + MinerU + Milvus + ES）
- `_search_course_chunks` **双路径分流**：`RAG_BACKEND=http-rag` 走外部服务，`local` 保留 FAISS/词法降级
- 上传附件**自动投递入库**（后台轮询至 `ready`，全程无人工干预）
- 权限**前置收窄**：先算可见 doc_id 白名单 → 传 `doc_ids`，不事后过滤
- 新增 `RagDocument` 映射表、`HttpRetrievalProvider`、统一 `http_client.py`（`trust_env=False` 绕代理）

**关键设计取舍**
- 边界：**rag-go 管"知识和证据"，edu 管"谁的、能看吗"**
- 入库走 **multipart 不走 from-object**：edu 无 MinIO 写入实现、bucket 不一致，multipart 反而省事且**支持自定义 doc_id**
- **score 不做阈值过滤**：实测 hybrid 返回 RRF 融合分（0.4~0.5）与 vector cosine（0.0167）**不是一个量级**

**量化证据（全绿）**
- 权限隔离正确：student01 见自己附件，02/03 不可见，教师/管理员全可见
- 降级正确：kill rag-go 后提问**返回 200 而非 500**
- 质量对比铁证：同一问题 local 返回 3 条全是词法打平的"提交：冒烟作业…"（**漏掉课程资料**），http-rag 精确命中真实段落

### 2.7 打通"视觉 → 业务"主线（毕设关键路径）

#### (1) 身份连接键修复 —— 让主线"成立"

**问题**：视觉侧 `vision_identities.student_no` 存学号 `S2024001`，业务侧 `users.username` 是 `student01`，
join 命中 **0 条** → `insight/engagement`、`insight/reports` 真实数据下**永远返回空**。

**方案（方案 A）**：`users` 新增 `student_no` 列，连接键改为 `vision_identities.student_no == users.student_no`。
（不选"把登录名灌进视觉层"——那会让视觉系统反向依赖业务命名规则，方向正好反了。）

**改动 8 处**：模型 + 运行期自动迁移（老库免手工迁移）+ 消费侧 join + Schema + 服务 + 种子 + 前端。

**量化证据**
- join 命中 **0 → 7**；`student01: 4 事件 / student02: 4 / student03: 0`
- `engagement` HTTP 200、`eventTotal=4`、`scenes=[lab_safety×3, classroom×1]`（此前恒空）
- 越权 403 未被破坏；唯一索引实测拒绝重复学号

#### (2) 告警规则引擎 —— 让主线"有说服力"

**问题**：视觉事件**只被"展示"，没有被"消费"**。49 项能力里只有 4 项真正消费视觉事件（8%）。

**方案**：新建告警规则引擎，事件落库后在同一事务内匹配 → 路由 → 去重 → 派发通知。
- `AlertRule` 表：名称 / 场景 / 等级阈值 / 通知学生 / 通知角色 / 去重窗口 / 启用
- `AlertRuleService.evaluate()`：等级过滤（info 不告警）→ 场景匹配 → 路由到人 → 去重 → 派发
- 派发失败 **try/except 包裹，不影响事件落库**
- 接口：`GET/POST /rules`、`PUT /rules/{id}/enabled`（仅 ADMIN 可写）

**量化证据**
- 闭环：跑 lab_safety 任务 → 两条 critical 事件 → `student01` 收 1 条（**只收自己的**）、`teacher01` 收 2 条
- 去重：同场景再跑一次，`student01` 告警数 **1 → 1**（未重复打扰）
- 权限：学生 `POST /rules` → **403**；非法场景 → **422**；路由数 **154 → 156**

## 三、技术要点速览

| 技术点 | 说明 | 价值 |
|---|---|---|
| **统一模型契约层** | Provider Registry + 模板方法 + 熔断/重试/超时 + 占位降级，4 类能力统一抽象 | 换模型只改环境变量，业务零改动 |
| **SceneState 统一中间表示** | YOLO 出像素级事实 → SceneState → 上层见状态不见图像 | 一套引擎支撑四场景，新增场景只实现 reasoner |
| **事件派生层** | 检测事实 → 语义事件的翻译规则表 + 三条自我约束 | "宁可少报，不伪造告警"，可信度可解释 |
| **常驻推理服务** | 进程级模型单例 + 双检锁 + 推理锁 + traceId 透传 | 65 倍性能提升 |
| **身份连接键对齐** | 学号作为业务标识贯穿视觉与业务两侧 | 打通"视觉→业务"最后一跳 |
| **规则引擎消费侧** | 事件 → 匹配 → 路由 → 去重 → 派发通知 | 视觉产出业务动作而非仅展示 |
| **权限前置收窄** | 先算可见白名单再检索，不事后过滤 | 避免召回缩水 + 越权内容不流转 |
| **零构建前端** | 原生 ES module + 内联 SVG sprite，离线可用 | 适配校园内网，无 CDN 依赖 |
| **自建 CDP 审计** | 裸 Node WebSocket 驱动无头 Chrome，真实登录逐页探测 | 109 条路由 0 异常，验证可复现 |
| **分层降级策略** | 外部服务不可用一律回落本地/占位，返回 200 不抛 500 | 单点故障不拖垮主流程 |

   并让熔断/重试/链路追踪等横切能力**零额外代码**自动覆盖新传输层。
2. **主线闭环**：发现并修复"视觉事件归属不到学生"的连接键断裂（join 命中 0 → 7），
   再补上告警规则引擎，把视觉从"只能展示"推进到"能派发业务动作"，让毕设核心主张从菜单主张变成事实。
3. **工程严谨性**：坚持"最精简证据"原则——占位模型宁可返回确定性结果也不编造；
   事件派生层只做阳性派生、不伪造告警；为验证前端自建 CDP 审计工具实测 109 条路由零异常。
