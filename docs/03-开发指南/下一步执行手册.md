## 零、先定三件事（动手前必须想清楚）

### 0.1 两个项目怎么分工 —— 这是最省时间的决定

| | `yolo-platform` | `edu-ai-platform` |
|---|---|---|
| 定位 | **视觉能力实验室** | **业务平台** |
| torch | `2.6.0+cu124`，CUDA ✅ | `2.13.0+cpu`，CUDA ❌ |
| 实测性能 | 26.63 ms / **37.6 FPS** | 153.75 ms / 6.5 FPS（CPU） |
| 该干什么 | 训模型、跑推理、验证算法 | 菜单、业务、接口接入 |

**结论：视觉相关的代码一律在 `yolo-platform` 写和跑，`edu-ai-platform` 只做接口接入。**

理由很硬：edu 那边的 torch 还是 CPU 版，要在那边跑 YOLO 得先重装 CUDA 版 torch
（又是 2.5 GB 下载 + 踩一遍今天踩过的坑）。而 yolo-platform 已经 37.6 FPS 跑通了。

**接入方式**：edu 通过 HTTP 或子进程调用 yolo-platform 的能力，
**不需要**在 edu 那边装 CUDA torch。这件事放到 M4 再做。

> 这条如果搞反了，你会花半天重装环境，而且大概率踩「pip 二次解析换回 CPU 版」那个坑。

### 0.2 剩余时间预算

按十一假期剩 3 天、每天有效 6–8 小时算，约 **18–24 小时**。
下面每个里程碑都标了预计耗时，**M0–M3 是必做（约 10–12 小时）**，
M4 之后按剩余时间取舍。

### 0.3 场景优先级的修正

我此前建议「先做拍照批改」，**现在改主意，建议先做课堂行为**。三条理由：

1. 课堂行为是你自己定的核心（"以课堂行为分析为核心"），核心场景不该排后面
2. 拍照批改涉及版面分析（轮廓检测 + 投影切割），是**独立的传统 CV 技术栈**，风险更高
3. 课堂行为的基础设施已经就绪 —— 检测链路今天已实测跑通，只差时序分析

代价是课堂行为需要**视频素材**（拍照批改只需静态图）。这是 M0 要准备的东西。

### M1 · 真实场景验证（0.5–1 h）🔴 —— 决策点

**目标**：把"预训练能直接顶上"从**推断**变成**实测证据**。

**为什么这一步最关键**：它决定你要不要训模型。训一个模型是假期里最贵的时间开销，
不训则省下大半天。**用一小时验证，换半天的确定。**

**动作**：建 `yolo-platform/scripts/bench_samples.py`，批量跑 samples 目录。

```python
"""批量跑 data/samples，统计教育相关类的命中情况。"""
import sys, time
from pathlib import Path
from collections import Counter

_ROOT = Path(__file__).resolve().parents[1]
sys.path.insert(0, str(_ROOT / "backend"))

from core.infer.predictor import load_model, predict_image  # noqa: E402

EDU_RELEVANT = {
    "person", "cell phone", "laptop", "book", "backpack", "handbag",
    "chair", "dining table", "keyboard", "mouse", "bottle", "cup",
}

def main():
    sample_dir = _ROOT / "data" / "samples"
    imgs = [p for ext in ("*.jpg", "*.jpeg", "*.png", "*.bmp")
            for p in sorted(sample_dir.glob(ext))]
    if not imgs:
        print("[X] data/samples 为空，先放图进来")
        return 1

    model = load_model("yolo11n.pt")
    hit, conf_sum = Counter(), Counter()
    total_edu = total_all = 0
    latencies = []

    for p in imgs:
        r = predict_image(model, p, conf=0.25)
        latencies.append(r.latency_ms)
        for d in r.detections:
            total_all += 1
            if d.cls_name in EDU_RELEVANT:
                total_edu += 1
                hit[d.cls_name] += 1
                conf_sum[d.cls_name] += d.conf

    print(f"\n图片数 {len(imgs)} | 检测总数 {total_all} | 教育相关 {total_edu}")
    print(f"平均延迟 {sum(latencies)/len(latencies):.1f} ms")
    print(f"\n{'类别':<14}{'命中':>6}{'平均置信':>10}")
    for k, v in hit.most_common():
        print(f"{k:<14}{v:>6}{conf_sum[k]/v:>10.3f}")
    return 0

if __name__ == "__main__":
    sys.exit(main())
```

**字段名已实测确认**（2026-10-03 读 `backend/core/infer/predictor.py`）：

| 对象 | 字段 |
|---|---|
| `InferResult` | `source` · `image_size` · `detections` · `latency_ms` · `device` · `model_path` · `classes_seen` · `count` |
| `Detection` | `cls_id` · `cls_name` · `conf` · `xyxy`（另有 `xywh` 属性与 `to_dict()`） |

**注意是 `cls_name` 和 `conf`**，不是 `label` / `confidence`。

**捷径**：`InferResult.classes_seen` 已经是 `dict[str, int]` 的类目计数，
只统计命中数的话可以直接用它，不必遍历 `detections`。
但**算平均置信度必须遍历** —— 所以上面脚本保留了遍历。

**运行**

```bash
cd ~/Desktop/yolo-platform
./.venv/Scripts/python.exe scripts/bench_samples.py
```

**验收**：出一张表，能看到 `person` 的命中数与平均置信度。

**决策点 —— 看 `person` 的平均置信度**

| 平均置信 | 结论 | 下一步 |
|---|---|---|
| **≥ 0.7** | 预训练直接可用 | **不训模型**，直奔 M2 |
| 0.5 – 0.7 | 勉强可用 | 不训，但 M3 里把 conf 阈值下调并加时序平滑 |
| **< 0.5** | 你的场景与 COCO 分布差异大 | 必须训，插入「数据集标注」阶段（半天起） |

**我预判是第一行。** COCO 的 `person` 是最鲁棒的类之一，室内正常光照下通常 0.8 以上。
跑出来如果是第三行，先别急着训 —— 检查是不是照片太暗 / 角度太偏 / 人太小，
**换素材比训模型便宜得多**。

### M2 · SceneState 契约定稿（2 h）🔴

**目标**：定下所有模块之间的数据契约。

**为什么必须现在做**：这是四个场景共用同一套结构的依据，
也是后面所有模块的接口。**契约定不下来，M3 写完还要返工。**

**动作**：在 `yolo-platform/backend/core/` 下建 `scenestate.py`，先只定义数据结构。

建议形态（可按你的判断调整字段名）：

```json
{
  "source": { "type": "video", "id": "classroom-01", "fps": 30 },
  "frame":  { "index": 1200, "timestampSec": 40.0 },
  "objects": [
    {
      "trackId": 7,
      "cls": "person",
      "conf": 0.88,
      "bbox": [412, 233, 498, 560],
      "keypoints": [[x, y, c], "..."],
      "identity": { "userId": 20230101, "seat": "3-2" }
    }
  ],
  "events": [
    {
      "type": "behavior",
      "trackId": 7,
      "label": "head_down",
      "durationSec": 182,
      "conf": 0.87,
      "evidence": { "rule": "pitch_angle > 35deg", "frameSpan": [5460, 5910] }
    }
  ]
}
```

**四条设计约束（别省）**

1. **`events` 必须带 `evidence`** —— 记录触发的规则与证据帧。
   答辩时"为什么判定他走神"全靠这个字段回答，规则推理的可解释性就体现在这。
2. **`identity` 允许为 null** —— 追踪到了但没绑定到真人时不能崩。
3. **`objects` 与 `events` 分离** —— 前者是瞬时观测，后者是时序结论。
   混在一起会导致下游无法区分"看到"和"判断"。
4. **时间统一用 `timestampSec`** —— 不要用帧号做对外契约，
   帧号依赖 fps，换个摄像头就全乱。

**验收**：拿一张图手动填出一个 SceneState JSON，确认四个场景（课堂/考场/实验室/拍照）
**都能填进同一个结构**。有一个填不进去，就是结构没设计对。

### M3 · 视觉核心链路（6–8 h）🔴

**目标**：视频进，结构化事件流出。这是整个系统的主干。

**分解**（建议按此顺序，每小步可独立验证）

| # | 子任务 | 预计 | 验证方式 |
|---|---|---|---|
| 3.1 | 视频抽帧 | 1 h | 每 N 帧取 1 帧，打印帧数 |
| 3.2 | 接入 BYTETracker | 2 h | 同一人在连续帧 `trackId` 稳定 |
| 3.3 | 姿态 → 行为规则 | 2 h | 单帧能判出 head_down / writing |
| 3.4 | 时序状态机 | 2 h | 持续时间 >30s 才升为事件 |
| 3.5 | 身份映射 | 1 h | `trackId` 能查到真实学生 |

**3.2 的关键坑**：`trackId` 会跳变（遮挡后重新分配）。
验证方法是**看一段视频里同一个人的 trackId 是否稳定**，
如果频繁跳变，说明 tracker 的 `track_buffer` 需要调大。

**3.4 的核心设计**：不要单帧就下结论。

```
单帧判定 head_down  →  只是观测
连续 N 帧（如 30s） →  才升格为事件
```

这一条直接决定系统可信度。**单帧判定必然误报**，
老师抬头看黑板的一瞬间被判成"抬头"是没有意义的。

**3.5 身份映射**：这是你相对纯视觉方案的**降维打击点**。
有 `enrollments` 业务表，才能把"有个学生在低头"升级为
"张三第 15 分钟起持续走神，且他前两次作业不及格"。
多数课堂行为分析的论文在这里就断了 —— 他们没有业务库。

**验收**：跑完一段视频，输出一个 `events` 数组，
里面至少有 1 条 `durationSec > 30` 的行为事件，且带完整 `evidence`。

### M4 · 接口接入（4–6 h）🟠

**目标**：让 `edu-ai-platform` 的 `/api/vision/overview` 返回真实数据。

**前置**：M3 完成。与 M5 可并行。

**关键点：不要把 CUDA torch 装到 edu 那边。** 两种接法：

| 方案 | 做法 | 适用 |
|---|---|---|
| **A. HTTP 转发**（推荐） | `yolo-platform` 起一个 FastAPI，edu 转发请求 | 两个项目长期分立 |
| B. 子进程调用 | edu 直接 `subprocess` 调 yolo 的 venv python | 快速验证，部署简单 |

**建议先走 B 跑通，再决定要不要换 A。** B 只需十几行代码，
能立刻看到效果；A 要处理服务发现、超时、重试，是工程化问题。

**验收**：`GET /api/vision/overview` 返回 200，且含 GPU 状态与今日推理量字段。

### M5 · 菜单迁移（3–4 h）🟠

**目标**：菜单按新结构显示。

**前置**：`menu.config.js` 已就绪。与 M4 可并行。

**顺序**（来自映射表文档，风险由低到高）：

1. 三个 dashboard 引入 `menu.config.js`，**先只渲染侧边栏**，业务 tab 走旧逻辑
2. **校对调性** —— 六项一级菜单摆出来，确认不像在线教育平台再继续
3. 迁 `teacher.py` / `student.py` → `/api/review/*`（纯换前缀，最安全）
4. 迁 `notifications.py` → `/api/situation/*`
5. 迁 `admin.py` → 拆分到 governance + situation
6. **`ai.py` 最后拆**

**验收**：三个角色的 dashboard 都能看到新菜单，且角色可见性正确。

### M6 · 场景扩展（剩余时间）🟢

按性价比排序：

1. **考场行为监测** —— 复用课堂行为的全部基础设施，

**考场监测排第一**是因为它几乎零额外成本：

## 附录 B · 环境笔记（今天踩过的坑，别再踩）

| 坑 | 现象 | 解法 |
|---|---|---|
| 官方源慢 | 0.1 MB/s，2.4 GB 要 6 小时 | 用 `https://mirror.sjtu.edu.cn/pytorch-wheels/cu124/`（2.16 MB/s） |
| 装成 CPU 版 | `torch.__version__` 带 `+cpu` | **版本号必须 pin 到含 `+cu124`**，且一次装完 |
| 二次装包被替换 | 装 ultralytics 时 torch 变 CPU 版 | 不要分两次 install |
| 模型落 CPU | CUDA 可用但跑在 cpu 上 | 显式 `.to(device)`，别信 ultralytics 自动选择 |
| 权重下载失败 | GitHub curl 28 超时 | 走 hf-mirror.com |

**自查口诀**：版本号后缀带 `+cpu` 就是装错了，正确应该是 `2.6.0+cu124`。
