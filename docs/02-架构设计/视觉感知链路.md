# 视觉感知链路：从「图片上传」到「语义事件」

> 本文记录一次真实断链的诊断与修复。所有结论均来自 `vision_tasks` / `vision_events`
> 表的历史记录与实测报文，不含推测。

---

## 一、问题：平台里的「上传的图片」与「被识别的图片」是两批数据

### 1.1 证据先摆出来

查 `vision_tasks` 历史记录（`provider` 字段说明实际跑的是哪个实现）：

| task | scene | source_ref | provider | 结论 |
|---|---|---|---|---|
| 5, 7 | paper_grading | `uploads/smoke/*.jpg`（**edu 路径**） | `placeholder` | edu 上传的图，但走占位实现 |
| 6, 8 | paper_grading | `.../ultralytics/assets/bus.jpg` | `yolo-platform` | 真推理，但**不是 edu 上传的** |
| 10 | classroom | `.../yolo-platform/storage/reports/smoke_detect.jpg` | `http-yolo` | 同上 |
| **11** | classroom | `uploads/smoke/*.jpg`（edu 路径） | `http-yolo` | **failed** ← 唯一一次「edu 路径 + 真模型」，失败 |
| 12 | classroom | `uploads/_probe/probe.jpg` | `http-yolo` | 探针，非业务上传 |

**结论：edu 的 `upload_file` 上传的图片，从未在真模型下跑通过。**

### 1.2 三处叠加的断链

**断链 A —— 上传接口不触发视觉分析。**
`app/routers/files.py` 的 `upload_file` 上传任何文件后只做两件事：落盘、投递知识库。
即使上传的是图片、即使 `category=SUBMISSION_ATTACHMENT`，也**不会**创建视觉任务。

**断链 B —— 两个核心场景没有入口。**
`classroom`（课堂行为）与 `lab_safety`（实验室安全）**完全没有**上传路径。
`register_pending_scan` 只覆盖 `paper_grading`，其余场景只能手填 `source_ref`
去调 `POST /api/vision/tasks` —— 这不是"接口"，这是"手工测试"。

**断链 C —— 真模型路径的事件恒为空（最隐蔽）。**
`app/core/models/adapters/_scene_mapping.py` 原本硬编码：

```python
state = SceneState(..., events=[], ...)
```

而 yolo-platform 在响应里自己写着：

> `"note": "检测由 yolo-platform 真实产出；语义事件由 edu 侧推理层生成"`

职责约定了，**edu 侧没实现**。后果反直觉：

> 换成真模型之后，平台功能**反而退化**了 —— 占位实现好歹会从"剧本"造出
> `head_down`「持续低头」这类事件，真模型路径却一条事件都没有，
> 于是「事件 → 学情 → 态势」整条消费链全部拿不到数据。

这就是此前审查中「视觉消费面仅 8%」的直接原因。

## 二、修复

### 2.1 上传即感知

`POST /api/files/upload` 新增**可选**参数 `vision_scene`：

```
POST /api/files/upload?category=TEMP_UPLOAD&course_id=1&vision_scene=classroom
```

- 不传 → 行为与从前**完全一致**（只落盘 + 投递知识库），向后兼容
- 传了且文件是图片 → 登记视觉任务，返回体带 `vision_task_code`
- 传了但文件不是图片 → `vision_task_code = null`，不误触发

**两种执行节奏，按场景区分（不是一刀切）：**

| 场景 | 节奏 | 理由 |
|---|---|---|
| `paper_grading` | **只登记 pending**，教师在工作台触发 | 批改结果影响分数，不能让模型跑完就落分 |
| `classroom` / `lab_safety` / `exam_proctor` | 登记后**立刻后台执行** | 这两类场景的语义就是「持续感知」，要人工逐个点就不成立 |

沿用入库投递同一条纪律：**登记同步（毫秒级，可返回 task_code），推理异步（后台跑）**。
推理冷启可能十余秒，绝不能拖住上传响应。

同时给登记加了**去重**：同一 `file_id` + 同一场景已有 pending 任务则复用，
学生重复提交同一份作业不会把待批改清单刷成一片重复项。

### 2.2 事件派生层（本次的核心）

新建 `app/core/models/adapters/_event_derivation.py`，把「检测事实」翻译成「语义事件」。

**三条自我约束 —— 宁可少产出，也不编造：**

1. **只做阳性派生，不做阴性判断。**
   检出某类目标 → 对应事件。但**不做**「没检出护目镜 → 没戴护目镜」这类推断：
   通用 COCO 权重的类别空间里根本没有 `goggles` / `gloves` / `lab_coat`，
   拿它的沉默去报「未佩戴」，等于把模型的短板说成学生的违规。
   无法判定的检查项会被如实列进 `summary.derivation.unverifiable_checks`。

2. **不做时序推断。**
   单帧图片推不出「持续低头」「频繁转头」「离座」，因此 `duration_s` 恒为 `0`，
   这类事件在单图路径上**不产出**。要做它们需要视频/流式输入，属于另一个能力等级。

3. **事件必须可追溯。**
   每条事件的 `evidence` 带上 `cls_name` / `conf` / `bbox` / `object_index`，
   人能拿着它回到原图核对。不可核对的告警不该进学情库。

**规则表**（类别名以视觉服务产出为准）：

| 场景 | 目标级事件 | 人数事件 |
|---|---|---|
| `classroom` | `cell phone`→`phone_detected`(warning)<br>`book`→`material_detected`(info)<br>`laptop`→`device_detected`(info) | `class_present` 在场人数 |
| `lab_safety` | `cell phone`→`phone_detected`(warning)<br>`fire`→`fire_detected`(**critical**)<br>`knife`→`sharp_tool_detected`(warning)<br>`bottle`→`reagent_detected`(info) | `operators_present` 实验区在场 |
| `exam_proctor` | `cell phone`→`phone_detected`(**critical**)<br>`book`→`material_detected`(warning)<br>`laptop`→`device_detected`(warning) | `candidates_present` 考场在场 |
| `paper_grading` | `question_block`→`block_located`<br>`handwriting`→`handwriting_detected` | — |

关键设计：

- **派生阈值 `max(request.conf, 0.35)`**：不低于检测阈值。事件再用更低的标准，
  等于把擦边框升级成告警。
- **人数事件取最弱置信度**：人数统计的可信度由最不确定的那个目标决定。
- **`RULE_VERSION = "1.0.0"`**：规则一改就升版本。同一份检测结果在不同规则下
  产出不同事件，不留版本号将无从追溯。
- **纯函数**：无随机、无时间依赖 → 可以拿历史检测结果**离线重放**，验证规则改动的影响面。

### 2.3 顺带修掉两处误导性输出

| 位置 | 原行为 | 修正后 |
|---|---|---|
| `/api/health` 的 `capabilities.*.default` | 报**注册默认值**（永远是 `placeholder`），会被误读成「视觉还在跑占位」 | 改报 `effective`（运行时生效值，配置优先），另列 `registered_default` |
| `/api/vision/overview` 的 `placeholders_in_use` | 遍历**所有已注册**实现，把「注册过占位」说成「正在使用占位」，配好真实后端后清单依旧不空 | 只报「当前生效的实现是占位」的能力 |

## 三、验证结果

### 3.1 首次打通完整链路

通过 edu 的上传接口上传一张真实图片（`vision_scene=classroom`）：

```
vision_tasks:
  scene=classroom | status=succeeded | provider=http-yolo | model=yolo11n.pt | is_placeholder=0
  file_id=5 | latency_ms=488.6
  source_ref=uploads/2026/10/09/ed97ce9fae5b4482a67366e0c7f29df0.jpg   ← edu 落盘的路径
  objects=5 (bus 0.94 + person×4)
  events=1 → class_present「在场人数 4」

vision_events:
  class_present | 在场人数 4 | sev=info | conf=0.622
  evidence: {"cls_name":"person","person_count":4,"source_type":"image","frame_id":0}
```

lab_safety 场景同样通过（139ms，产出 `operators_present 实验区在场 4 人`）。

### 3.2 验证清单

| 验证项 | 结果 |
|---|---|
| edu 上传图片 → 自动登记 → 后台推理 → 真模型落库 | ✅ 首次打通 |
| 事件落库并可被消费端读取（`/api/vision/events`） | ✅ |
| `paper_grading` 只登记不自动跑（人工复核边界） | ✅ 停在 `pending`，`result_json=None` |
| 非图片 + `vision_scene` 不误触发 | ✅ `visionTaskCode=null` |
| 不传 `vision_scene` 时行为与从前一致（向后兼容） | ✅ |
| 登记去重（同 file+scene 复用） | ✅ 两次登记返回同一 task_code |
| 场景隔离（同 file 不同 scene 不误复用） | ✅ |
| 作业提交链路回归 | ✅ 上传附件后提交 → 自动登记 pending，总数 1→2 只增 1 条 |
| `placeholders_in_use` 修正后 | ✅ `['embedding:placeholder','llm:placeholder']` |

### 3.3 一个有说服力的对比

| | 事件 | 性质 |
|---|---|---|
| 旧**占位**实现 | `no_goggles 未佩戴护目镜 / critical` | **编的**——权重根本不认识护目镜 |
| 新**真模型**路径 | `operators_present 实验区在场 4 人`<br>+ `unverifiable_checks` 声明「护目镜判断需专用权重」 | 只报能验证的，并公开能力边界 |

即「宁可少报，不伪造告警」——这正是视觉系统可信度应有的姿态。

## 四、答辩要点

1. **分层清晰的职责边界**：视觉服务出「像素事实」，edu 出「语义解释」。
   两边各自可独立替换（换权重、换场景规则），靠 `SceneState` 契约解耦。

2. **不编数据是一条硬原则**。派生层宁可零事件，也不把模型不认识的类别
   说成学生违规；同一原则也体现在拍照批改「只定位题块、不给分数」上。

3. **能力边界显式化**。`unverifiable_checks` 让「没有事件」这件事可解释 ——
   是画面干净，还是这块判断不具备条件，一眼分得清。

4. **两套节奏对应两类业务**。批改需人工复核（分数敏感），课堂/实验室感知要自动跑。
   用同一套登记机制 + 场景开关实现，没有为两种需求写两套代码。

---

## 五、遗留

1. **身份映射仍无法生效**：`vision_identities` 表按座位号（`R1-C1`）映射学号，
   但通用 COCO 权重不产出座位信息，因此事件的 `subject_ref` 恒为 `null`
   —— 事件知道「有人」，不知道「是谁」。需要专用权重或座位标定流程。
2. **连接键断裂未修**：`vision_identities.student_no = 'S2024001'` 而
   `users.username = 'student01'`，两表按学号 join 结果为 0 条。
3. 四个外部依赖（MinIO / ES / Milvus / rag-go）无统一编排脚本。
4. 当前验证使用通用 COCO 权重（`yolo11n.pt`），语义与场景不匹配
   （用它测「课堂行为」只是验证链路连通性）；正式效果需自训练权重。
