## 一、当前环境是否已部署可用模型

### 1.1 实测结论：没有可用的生成式模型

| 检查项 | 实测结果 | 判定 |
|---|---|---|
| `OLLAMA_MODEL`（本地生成模型） | **EMPTY** | ❌ 未配置 |
| `OPENAI_API_KEY` | **EMPTY** | ❌ 未配置 |
| `ANTHROPIC_API_KEY` | **EMPTY** | ❌ 未配置 |
| `DASHSCOPE_API_KEY` | **EMPTY** | ❌ 未配置 |
| `EMBEDDING_MODEL` | 已设置（本地 HF 模型） | ✅ 仅嵌入可用 |
| ollama 服务 | 运行中，模型仅 `bge-m3:latest`（1.2 GB） | ⚠️ 嵌入模型，非生成式 |

**直接后果**：`ai/llm.py` 的 `get_llm()` 会走到最后一行抛出
`ValueError("No LLM provider is configured; set OLLAMA_MODEL or an API key")`。
也就是说现在任何依赖 LLM 的链路（学习计划、批改建议、RAG 问答）**都跑不起来**。

**唯一现成资产**：`bge-m3` 是嵌入模型，RAG 的检索侧是通的，缺的只是生成侧。
这是一件好事——意味着你做 RAG 增强时，检索这半边不用重做。

### 1.2 硬件余量（实测）

| 资源 | 数值 | 说明 |
|---|---|---|
| GPU | RTX 4060 Laptop | 驱动 560.94 |
| 显存 | 总 8188 MiB / 已用 416 MiB / **可用 7542 MiB** | 决定能跑哪一档模型 |
| 磁盘 C 盘 | 剩余 **84 GB** | 每个模型 1.2–9 GB，够放 5–8 个 |

### 1.3 拉取通道可用性（实测）

```
ollama --version            -> 0.33.3
registry.ollama.ai 握手     -> 可达，1.33s
```

网络通，可以拉取。但 **GitHub Releases 直连会超时**（同项目内测过，curl 28），
拉取大模型权重时若走 GitHub 源需准备镜像。

### 1.4 拉取/接入的前置条件清单

| 维度 | 要求 | 本机状态 |
|---|---|---|
| **显存** | Q4_K_M 档：4B≈3GB / 8B≈5.5GB / 14B≈9GB | 7.4GB 可用 → **上限 8B（Q4）** |
| **依赖** | ollama ≥0.6 或 vLLM/llama.cpp | ollama 0.33.3 ✅ |
| **磁盘** | 单模型 1.2–9GB + 预留 20GB 给评测数据 | 84GB ✅ |
| **权重来源** | ollama library / HF / ModelScope；GitHub 需镜像 | registry 可达 ✅ |
| **许可协议** | 商用前必须逐模型确认（见第二节） | 待逐项核对 |
| **数据合规** | 涉及未成年人学习数据，**优先本地部署** | 本地路径可行 ✅ |

> ⚠️ **8GB 显存的硬约束**：Qwen3-14B Q4_K_M 需 ~9GB，本机跑不了；
> 即便 8B 也要**关闭或限制 thinking 模式**——thinking 会让 KV cache 增加 2–3 倍，
> 建议 context 限制在 8K–16K。这是本机最容易踩的坑。

## 三、候选模型推荐（针对 8GB 显存，5 选 3 起步）

**筛选逻辑**：显存 7.4GB 是硬闸门 → 上限 8B（Q4）→ 优先选有教育微调的版本 → 保留一个通用基线做对照。

| # | 模型 | 规模/量化 | 显存 | 学科问答 | 解题讲解 | 适龄表达 | 拒答与安全 | 取舍 |
|---|---|---|---|---|---|---|---|---|
| 1 | **Qwen3-8B** (Q4) | 8B Q4_K_M | ~5.5GB | ★★★★ | ★★★★ | ★★★ | ★★★★ | **本机质量上限**，通用基线；thinking 需限 8K |
| 2 | **Qwen3-4B** (Q4) | 4B Q4_K_M | ~3GB | ★★★ | ★★★ | ★★★ | ★★★★ | 最轻量，可开 thinking，适合做**对照组与快速迭代** |
| 3 | **OmniEdu-4B / 9B** | 教育微调 | ~3 / ~6GB | ★★★★★ | ★★★★★ | ★★★★ | ★★★★ | **教育增益最明确**；9B 需确认显存与权重可用 |
| 4 | **EduChat-R1-Qwen3-8B** | 教育+推理 | ~5.5GB | ★★★★ | ★★★★★ | ★★★★ | ★★★★ | 推理链长→**延迟高**，8GB 卡需限 context |
| 5 | **Xinghuo X2.5-4B** | 端侧开源 | ~3GB | ★★★★ | ★★★★ | ★★★ | ★★★ | 数学强、1M 上下文；**许可需逐条确认商用范围** |

**我的建议组合（先跑 3 个）**：

1. **Qwen3-4B** —— 当"对照组 + 快速迭代机"，冷启动快，改提示词能立刻看效果。
2. **Qwen3-8B** —— 当"本机质量天花板"，用来判断 4B 的差距到底有多大。
3. **OmniEdu-4B 或 EduChat-R1-Qwen3-8B** —— 当"教育专用价值验证"，
   用来回答那个关键问题：**教育微调到底值不值得**（这直接决定要不要走微调路线）。

> 打分是本方案下的相对判断（★ 数量），**不是公开榜单分数**。
> 真实排序必须由你自己跑第四节评测集得出——这正是下一步要做的事。

## 四、可执行测试方案

### 4.1 轮次安排

| 轮次 | 目标 | 模型 | 产出物 | 通过标准 |
|---|---|---|---|---|
| **R0 冒烟** | 打通链路，确认能出字 | 1 个（Qwen3-4B） | `smoke_llm.json` | 3 个学科各 1 题均能返回非空、延迟可测 |
| **R1 基线** | 建立可比基线 | 全部 3 个 | `eval_r1.csv` + 汇总表 | 每模型每学科 ≥30 题，评分口径跑通 |
| **R2 提示词** | 验证提示词工程的增益 | 最优 1–2 个 | `eval_r2.csv` + 提示词版本 | 相对 R1 有可量化提升（≥5 分） |
| **R3 检索增强** | 验证 RAG 增益（用现成 bge-m3） | 最优 1–2 个 | `eval_r3.csv` | 事实类题准确率提升，且无检索污染 |
| **R4 微调决策** | 判断是否值得微调 | — | 决策报告 | 见第五节达标线 |

**关键纪律**：R1→R2→R3 每轮**只改一个变量**，否则无法归因。

### 4.2 评测集构建

**三维度交叉设计**（建议总量 180–300 题，先做 60 题小样本跑通流程）：

| 维度 | 取值 | 配比建议 |
|---|---|---|
| **学科** | 数学、物理、化学、生物、语文、英语 | 数学 30%（你场景的核心），其余各 14% |
| **题型** | 单选、填空、计算/解答、概念讲解、作文批改 | 客观 50% / 主观 50% |
| **学段** | 小学、初中、高中 | 按目标用户定，建议高中 50% |

**每道题记录字段**：

```json
{
  "id": "math_hs_0031",
  "subject": "math",
  "grade": "high",
  "qtype": "solution",
  "question": "题干原文",
  "ref_answer": "标准答案/评分要点",
  "rubric": "步骤分分配说明",
  "source": "教材/真题/自编",
  "age_sensitive": false,
  "safety_tag": null
}
```

**来源优先级**：真题/教材 > 自建 > 网络采集（网络题答案准确性需人工复核）。
**务必记录 `source`**，毕设答辩时"数据从哪来"必被问。

### 4.3 评测指标与打分标准

| 指标 | 计算方式 | 权重 | 说明 |
|---|---|---|---|
| **答案准确率** | 客观题：0/1；主观题：对比 rubric 给 0–3 分 | 35% | 核心指标 |
| **步骤完整度** | 0–3 分：无步骤/有残缺/完整/完整且规范 | 20% | 教育场景的关键差异点 |
| **适龄性** | 0–3 分：术语是否超纲、表述是否匹配学段 | 15% | 通用模型常见短板 |
| **拒答与安全** | 该拒答时拒答得 1 分，误拒扣分 | 15% | 需专门构造 10–15 条诱导题 |
| **幻觉率** | 出现无依据事实的次数 / 总题数 | 10% | 越低越好 |
| **延迟 / 吞吐** | 首字延迟、tokens/s | 5% | 影响可用性 |

**判卷方式（三级）**：

1. **客观题自动判**：答案比对脚本，0/1。
2. **主观题 LLM-as-judge**：用一个**与被评模型不同厂商/不同系列**的模型打分，
   避免自评偏差；打分时给出理由。
3. **人工抽检**：每轮每学科抽 10% 复核，计算 judges 与人工的一致率。
   一致率 <70% 说明 rubric 写得不够清楚，必须先改 rubric 再继续。

> ⚠️ 这是最容易被忽视也最致命的一环：**judge 不校准，后面所有分数都是自娱自乐。**

### 4.4 基线对比方法

- **同题、同提示词、同温度**（建议 temperature=0.2，减少随机性）。
- 每个模型跑**同一份评测集**，不允许"这个模型跑这套、那个模型跑那套"。
- 结果以「模型 × 学科 × 题型」三维交叉表呈现，便于定位短板。
- **外部参照**：把 GAOKAO-Bench 类公开分数单列一栏做旁证，
  但**不与你的自测分数直接比较**（判卷口径不同）。

### 4.5 每轮结论记录模板

```markdown

| 学科 | 准确率 | 步骤分 | 适龄 | 拒答 | 幻觉率 | 加权总分 |
|---|---|---|---|---|---|---|
| 数学 | | | | | | |
| ... | | | | | | |
```

## 五、微调的前置条件与过渡路径

### 5.1 必须先满足的三个门槛

**门槛一：数据量与质量**

| 项 | 建议阈值 | 说明 |
|---|---|---|
| 样本量 | **≥500 条**起步，1000–2000 条较稳 | 低于 300 条大概率不如提示词工程 |
| 学科覆盖 | 每个目标学科 ≥80 条 | 避免偏科 |
| 准确性 | 人工复核通过率 **≥95%** | 错误数据比没数据更糟 |
| 格式一致性 | 100% 符合既定模板 | 含步骤标记、适龄标注 |
| 去重 | 相似度 >0.9 的样本需合并 | 重复数据会放大偏见 |

**门槛二：评测基线达标线**

满足以下**全部**才建议进入微调：

- R2（提示词优化后）加权总分 **≥70 分**（百分制）
- R3（RAG 后）相对 R2 提升 **<5 分** ← **关键信号**：
  **说明检索和提示词已经榨干了，剩余差距只能靠改模型权重**
- 短板集中在**风格与规范**（如步骤写法、适龄表述），
  而非**知识缺失**（知识缺失应优先做 RAG，不是微调）
- 已积累 ≥500 条可复用的人工修正样本

> 最后一条是判断的核心：**如果差距来自知识，做 RAG；如果差距来自风格，才做微调。**

**门槛三：算力与成本预算（本机 8GB 场景）**

| 方案 | 可行性 | 说明 |
|---|---|---|
| 全参微调 7B | ❌ | 显存远远不够 |
| **QLoRA 4B** | ✅ **推荐** | 8GB 显存可跑，需约 6–8GB |
| QLoRA 7B | ⚠️ 勉强 | 需 offload，速度慢，batch=1 |
| 云端 A10/A100 租用 | ✅ | 按小时计费，适合短期冲刺 |

**预算参考（自用验证级）**：本地 QLoRA 微调 4B，1000 条数据、2–3 个 epoch，
本机约数小时；若租云 GPU，按量计费通常几十元级即可完成一次实验。

### 5.2 三段式过渡路径

```
阶段 A：提示词工程（零成本，先榨干）
   ↓  达标线：R2 提升 <5 分 / 轮
阶段 B：检索增强 RAG（用现成 bge-m3，补知识短板）
   ↓  达标线：R3 提升 <5 分
阶段 C：微调（改权重，解决风格与规范问题）
```

**不要跳步。** 直接从 A 跳到 C 是新手最常见的浪费——
多数"模型不行"的问题，其实是提示词和检索没做好。

### 5.3 数据留存建议（从第一天就要做）

微调数据不是最后才收集的，而是**评测过程中自然沉淀**的。建议建三张表：

| 表 | 内容 | 用途 |
|---|---|---|
| `eval_items` | 题目、标准答案、rubric、来源 | 评测集复用与版本管理 |
| `eval_records` | 每次调用的 model/版本/prompt/响应/评分 | **可复现的关键**，没有它无法归因 |
| `corrections` | 人工修正后的优质回答 | **微调数据的直接来源** |

**必须记录的元信息**（缺一项就无法复现）：

```
model_name + model_version + model_digest(ollama 的 sha256)
prompt_template_version
temperature / top_p / max_tokens
run_timestamp
```

> ollama 的模型 digest 尤其重要：同名 tag 会被重新拉取覆盖，
> 只记 `qwen3:4b` 而不记 digest，三个月后你根本不知道当时跑的是哪一版。

## 六、最小验证流程（本机可跑，实测通道已通）

```bash
# R0-1 拉取最小模型，验证通道（约 500MB，几分钟）
ollama pull qwen3:0.6b

# R0-2 冒烟：确认能出字
ollama run qwen3:0.6b "用初中生能听懂的话解释什么是勾股定理"

# R0-3 正式候选（按显存余量选，别一次全拉）
ollama pull qwen3:4b      # ~3GB  Q4 档，主力迭代
ollama pull qwen3:8b      # ~5.5GB，本机质量上限

# R0-4 接入项目：改写 .env
OLLAMA_MODEL=qwen3:4b
OLLAMA_BASE_URL=http://localhost:11434
```

**显存告警线**：8B 模型 + thinking 模式 + 长上下文会撑爆 8GB。
出现明显变慢时，先 `nvidia-smi` 看是否 spill 到内存——
**宁可换小一档，也不要让模型半装载**（实测半装载会从 40 tok/s 掉到 8 tok/s）。

### 6.1 实测踩坑：thinking 模式会吃掉 token 预算（2026-10-03 实测）

用 `qwen3:0.6b` 跑同一道勾股定理题，两种配置对比：

| 配置 | 延迟 | tokens | 速度 | 答案长度 | 结果 |
|---|---|---|---|---|---|
| 默认（thinking 开） | 4.6s | 600 | 129 tok/s | 114 字 | ❌ **被截断**（停在 `c² =`） |
| `<arg_key:6124c78e>` 关闭思考 | 3.9s | 507 | 132 tok/s | 208 字 | ✅ 完整解出 c=5 |

**结论**：qwen3 系列默认开启 thinking，思考过程会占用 2/3 左右的 token 预算。
若 `num_predict` 设得不够大，**最终答案会被截断**——
在评测里这会表现为「步骤不完整」而**被误判为能力差**，实际上只是预算不够。

**对评测方案的两条硬性要求**：

1. **评测时必须显式固定 thinking 开关**（在 prompt 末尾加 `<arg_key:6124c78e>`，或统一开启），
   并把这个开关写进 `eval_records` 的元信息。不固定则多模型之间分数不可比。
2. `num_predict` 要留足余量；建议先关 thinking 跑一遍拿基线，
   再单独设计一组「开启思考」的实验考察推理增益。

> 8GB 显存上这一点尤其致命：thinking 既吃 token 预算，
> 又让 KV cache 增大 2–3 倍，两头挤压。
