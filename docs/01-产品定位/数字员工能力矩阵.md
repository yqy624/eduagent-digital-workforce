# 数字员工能力矩阵

> 一句话：员工 = 岗位 + 可读数据 + 可用工具 + 写权限级别。
> 本文是 `static/js/desktop/employees.js` 里五位内置员工的说明版，写给要用、要改、要演示的人看。

## 一、总览

| 员工 | 岗位 | 写权限 | 落库前是否需要人工确认 | 主要接口前缀 |
|------|------|--------|------------------------|--------------|
| 知问 | 答疑员工 | `read` | —（只读，不写库） | `/api/knowledge` |
| 笔正 | 批改员工 | `write-gate` | 是，教师确认后写成绩 | `/api/review` |
| 明察 | 视觉员工 | `write-event` | 否（只写事件，不改成绩） | `/api/vision` |
| 知微 | 学情员工 | `read` | —（只读，产出报告） | `/api/insight` |
| 守则 | 督导员工 | `write-gate` | 是，按规则触发并留处理记录 | `/api/situation` |

写权限的三种取值对应三种行为：

- `read`：只能查与算，任何写请求都会被拒。
- `write-gate`：可以产出「待确认」的结果，必须有人点确认才真正落库。
- `write-event`：可以写事件（属于「记录发生了什么」），但不能改业务结论（成绩、名单）。

## 二、逐个说明

### 知问 · 答疑员工

- **职责**：回答学生关于课程和作业的问题，每条答案附资料出处；资料里没有就直说找不到，不编。
- **读什么**：课程资料、常见问题、作业要求。
- **可用工具**：`get_course_overview`、`get_course_assignments`、`retrieve_course_material`。
- **产出**：带引用的回答（引用指向课程文档片段）。
- **典型问法**：「这次作业的交作业时间」「第三章讲了什么」「评分标准里格式分怎么算」。
- **边界**：检索为空时不生成答案，直接回「资料里没有」。这是设计选择，不是失败。

### 笔正 · 批改员工

- **职责**：对照评分标准逐题看作答，给出各题得分、错因和评语；最终成绩要教师确认才计入。
- **读什么**：学生提交（文本/附件）、作业要求、评分标准、同类历史评语。
- **可用工具**：`get_course_assignments`、`get_course_statistics`。
- **产出**：逐题得分 + 错因 + 评语，状态为「待确认」。
- **人工确认点**：教师在「确认批改建议」里采纳或改写后才写成绩。
- **边界**：不代替教师给最终分；不修改已确认的成绩。

### 明察 · 视觉员工

- **职责**：盯课堂、实验室、作业和考试的影像，发现异常第一时间报；只负责发现，怎么处理由人定。
- **读什么**：上传的图片/视频帧，场景配置（课堂行为、考场、实验室安全、拍照批改）。
- **可用工具**：`retrieve_course_material`（用于对照规范条文）。
- **产出**：视觉事件（场景、严重度、置信度、学生归属），写入 `vision_events`。
- **链路**：上传 → YOLO 推理 → 类别映射 → 规则派生语义事件 → 落库 → 触发告警规则。
- **边界**：视觉侧只输出「画面里有什么」（COCO 类别），语义判断在业务侧规则里；
  因此换场景改规则即可，不需要重训模型。拍照批改是例外，需要专用类别权重。

### 知微 · 学情员工

- **职责**：把成绩、课堂表现和作业情况汇总，找出薄弱环节并给改进建议，不替人下结论。
- **读什么**：成绩、提交记录、课堂参与度、作业完成情况。
- **可用工具**：`get_my_grades`、`get_my_submissions`、`analyze_learning_gaps`、
  `generate_learning_plan`、`get_course_statistics`。
- **产出**：学情诊断与学习计划（一周粒度，含推荐练习）。
- **边界**：计划是建议不是任务派发；学生可自行调整。

### 守则 · 督导员工

- **职责**：按设定条件留意异常，需要时通知相关人；同一条提醒不会重复打扰。
- **读什么**：视觉事件、告警规则（严重度、场景、去重窗口）、通知记录。
- **可用工具**：`send_notification`、`get_course_statistics`。
- **产出**：提醒（站内通知 + 实时推送），并记录处理状态。
- **人工确认点**：规则的启停与阈值由管理员设定；提醒的处理由教师或管理员标记。
- **边界**：`info` 级事件不告警；同类提醒在去重窗口内只发一次。

## 三、员工之间怎么协作

```
明察（发现异常）
   └─ 事件落库 ─→ 守则（按规则提醒）─→ 通知中心 / 实时推送
笔正（批改建议）
   └─ 待确认 ─→ 教师确认 ─→ 成绩写回 ─→ 知微（学情汇总）
知问（答疑）
   └─ 引用课程资料 ─→ 学生自助解决，减少重复提问
知微（学情诊断）
   └─ 薄弱点 ─→ 推荐资料（回到知问的检索范围）
```

关键点：**员工之间不直接调用彼此**，都通过业务数据与事件解耦。
删掉或停用某个员工，其余员工照常工作。

## 四、新增自定义岗位

在协作台「员工」页新建岗位时需要填：

| 字段 | 说明 | 约束 |
|------|------|------|
| 名称 | 员工叫什么 | 必填，界面展示用 |
| 岗位 | 一句话岗位名 | 默认「自定义岗位」 |
| 职责描述 | 面向用户的说明：它替你做什么 | 不要写实现细节（模型、库表、规则引擎） |
| 数据域 | 它能读的数据范围 | 与权限模型对齐，不能越出角色可见范围 |
| 图标与配色 | 界面标识 | 从内置图标与配色里选 |
| 写权限 | `read` / `write-gate` / `write-event` | 默认 `read`，需要写库必须显式升级 |
| 工具 | 可调用的工具集合 | 只能从已注册工具里选，未注册的不会被加载 |

默认新员工是停用状态，配置完再启用 —— 避免一个没配好的员工被误派活。
