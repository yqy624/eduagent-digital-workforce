# 身份连接键修复说明 · 2026-10-10

> **主题**：打通「视觉事件 → 学生」的最后一跳，让"以视觉为核心"从主张变成事实
> **对应交接文档**：`交接文档_2026-10-09_视觉链路与RAG外置.md` §4 P0 #1 / §5 第一优先
> **状态**：✅ 已完成并端到端验证

---

## 1. 问题：主线断在最后一跳

毕设要论证的是「**视觉是源、教育业务是消费方**」。2026-10-09 的交接文档指出：视觉链路本身已通，
但 `insight`（学情洞察）这条消费链在真实数据下**永远返回空**。

**修复前实测**（`data/platform.db`）：

| 事实 | 值 |
|---|---|
| `vision_identities.student_no` | `S2024001 / S2024002 / S2024003`（学号） |
| `users.username` | `student01 / student02 / student03`（登录名） |
| `users` 是否存在 `student_no` 列 | **不存在** |
| `join i.student_no = u.username` 命中 | **0 条** |

→ `insight/engagement`、`insight/reports` 的连接键正是这两者相等，因此**恒为空**。

**根因**：学号与登录名是两套命名空间，被当成了同一个东西。视觉侧存学号是对的，
错的是业务侧（`users`）根本没有"学号"这个字段，只能拿 `username` 顶替。

---

## 2. 方案：给业务侧补上学号

**方案 A（已采用）**：`users` 新增 `student_no` 列，连接键改为
`vision_identities.student_no == users.student_no`。

**为什么不选方案 B**（`vision_identities.student_no` 改存 `student01`）：
那等于把登录名灌进视觉层，视觉系统从此依赖业务系统的登录命名规则 —— 方向正好反了。
学号才是学生的**真实业务标识**，缺字段的是业务表。

**边界**：教师 / 管理员没有学号，`student_no` 可空；同一学号不允许绑定到两个账号（唯一索引）。

---

## 3. 改动清单

| 层 | 文件 | 改动 |
|---|---|---|
| 模型 | `app/models/models.py` | `User` 新增 `student_no`（`String(64)`，可空）+ 唯一索引 `uq_users_student_no` |
| 迁移 | `app/database.py` | `ensure_runtime_schema` 补列 `users.student_no` + 新增 `_add_index_if_missing` 补唯一索引（老库免手工迁移） |
| 消费 | `app/routers/insight.py` | `engagement` / `reports` 两处连接键改为 `target.student_no`；学号为空时返回明确提示而不静默返回空；响应字段 `student_no` 改回真实学号 |
| Schema | `app/schemas/auth.py` | `LoginResponse` / `UserResponse` / `ProfileResponse` 增加 `student_no`；`RegisterRequest` 支持写入学号 |
| 服务 | `app/services/auth_service.py`、`app/services/admin_service.py` | 登录 / 注册 / 建档 / 创建用户均携带 `student_no` |
| 种子 | `scripts/seed_demo.py` | `USERS` 增学号列（与 `SEATS` 一致）；**对已存在的账号幂等回填学号** |
| 前端 | `static/js/console/pages/vision.js` | 身份绑定表单「学号」改为必填（后端本就走 `min_length=1`，此前前端允许留空会 422） |

## 4. 验证证据（全部实测）

**库层**：连接命中 `0 → 7` 条；按学生统计事件数 `student01: 4`、`student02: 4`、`student03: 0`。

**API 层**（TestClient，`DB_BACKEND=sqlite`）：

| 用例 | 结果 |
|---|---|
| `GET /api/insight/students/3/engagement` | HTTP 200；`studentNo=S2024001`、`identityCount=3`、`eventTotal=4`、`scenes=[lab_safety×3, classroom×1]`、`bySeverity={critical:3, warning:1}`、`note=''` |
| `POST /api/insight/reports` | HTTP 200；`visionEventCount=4`、`vision.identityCount=3`、`note=''` |
| 有身份无事件（student03） | `identityCount=1`、`eventTotal=0`、`note=''`（正确：映射在，只是没有事件） |
| 无学号主体（teacher01） | `studentNo=None`、`note='该学生尚未登记学号（users.student_no）…'`（不再静默返回空） |
| 越权（student01 查 student03） | HTTP 403 —— 鉴权未被破坏 |
| 注册含学号 → 登录回显 | `studentNo=S2099001` 正常往返 |
| 唯一索引 | 重复学号写入被拒：`UNIQUE constraint failed: users.student_no` |
| 整体冒烟 | `/api/health` HTTP 200 `status=ok`；路由数 154 不变 |

> **注意**：响应体键名经中间件转 camelCase（`student_no` → `studentNo`），
> 请求体仍必须 snake_case —— 老坑，勿踩。

## 5. 这条修复对毕设的意义

现在有了**第一条真正跑通的"视觉 → 业务"闭环**：

```
上传图片 → YOLO 推理 → 视觉事件落库 → 按座位映射到学号 → 学号归属到学生 → 参与度 / 学情报告
```

答辩时可直接演示：同一张实验室照片进来，系统产出 `no_gloves / critical` 事件，
并把它归到 `S2024001`（李同学）名下，参与度页与学情报告同步出现该行为数据。
这比"菜单里有视觉模块"有说服力得多。
